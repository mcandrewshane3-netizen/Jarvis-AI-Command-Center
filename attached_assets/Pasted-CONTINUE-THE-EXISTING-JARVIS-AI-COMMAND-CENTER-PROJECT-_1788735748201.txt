============================================================
JARVIS REAL IPAD SAFARI / PWA LAYOUT REPAIR
============================================================

PRIMARY OBJECTIVE:

Repair the existing JARVIS interface so it correctly fills and responds to the
REAL viewport of an iPad running Safari and, later, standalone PWA mode.

A real-device screenshot showed that previous simulated iPad validation was not
sufficient.

DO NOT simply make elements smaller.

Fix the responsive layout architecture.

============================================================
OBSERVED REAL-IPAD PROBLEMS
============================================================

On actual iPad Safari in LANDSCAPE:

1. The application does not use the available viewport correctly.

2. The main conversation region ends prematurely vertically.

3. A very large unused blank region appears below the conversation.

4. Conversation cards can extend beyond / become clipped by their intended
container.

5. The right intelligence/activity rail contains cards that are partially clipped
at the bottom.

6. The three-column desktop cockpit is consuming too much usable width.

7. The left navigation remains desktop-sized and consumes excessive horizontal
space.

8. Scrolling behavior between:
   - page
   - conversation
   - left navigation
   - right intelligence rail
   is not properly isolated.

9. The central conversation/composer experience is not behaving like a
full-height application workspace.

10. Safari browser chrome changes the actual usable viewport.

11. Previous responsive/browser-preview tests passed despite the real device
being visibly incorrect.

Treat the REAL iPad screenshot/behavior as authoritative.

============================================================
PART 3 — APPLICATION SHELL
============================================================

Create/repair a true full-viewport application shell.

Conceptually:

JARVIS APP
├── navigation
├── main workspace
│   ├── conversation
│   └── contextual intelligence
└── persistent interaction/composer area

The shell should occupy the available dynamic viewport.

Avoid BODY-level scrolling for normal JARVIS operation where possible.

The app should behave like an application, not a long desktop webpage.

============================================================
PART 4 — LANDSCAPE IPAD LAYOUT
============================================================

For typical modern iPad landscape widths:

preserve the cinematic cockpit experience,

BUT optimize usable space.

Preferred behavior:

LEFT NAV
compact/collapsible

CENTER
conversation gets dominant width

RIGHT RAIL
contextual intelligence gets secondary width

Do not give all three regions rigid desktop widths.

Use responsive grid/flex sizing such as:

compact nav
minmax(0, 1fr) conversation
bounded contextual rail

Ensure center column cannot overflow because of flex/grid min-content behavior.

Use min-width: 0 where required.

============================================================
PART 5 — COLLAPSIBLE NAVIGATION
============================================================

On iPad:

allow the left navigation to collapse to a compact icon rail.

Provide an obvious control to expand it.

Expanded navigation should overlay or temporarily consume space rather than
permanently starving the conversation area when appropriate.

Preserve all existing navigation destinations.

Desktop can retain the fuller navigation.

============================================================
PART 6 — RESPONSIVE RIGHT RAIL
============================================================

The contextual intelligence/right rail must not force the center conversation
into an unusable width.

On larger landscape iPads:

show the rail when sufficient space exists.

On narrower landscape or portrait:

collapse it into a drawer/panel accessible from an obvious control.

Do not simply hide its functionality.

Its internal content should have its own vertical scrolling when necessary.

============================================================
PART 7 — CONVERSATION WORKSPACE
============================================================

The conversation area should use all remaining available vertical space.

Required structure:

conversation header/status if applicable
→ scrollable message history
→ persistent composer/voice controls

The MESSAGE HISTORY should scroll.

The entire application shell should not need to scroll simply to reach the
composer.

Fix:

clipped messages
premature conversation boundaries
large blank lower area
incorrect overflow
composer displacement

Use:

min-height: 0
min-width: 0
overflow-y: auto

appropriately within flex/grid children.

============================================================
PART 8 — COMPOSER
============================================================

The text/voice composer must remain reachable and visually stable.

It should remain at the bottom of the conversation workspace.

Account for:

Safari bottom chrome
PWA standalone mode
safe-area inset
on-screen keyboard

When the keyboard opens:

the composer should remain visible.

Do not allow the keyboard to permanently corrupt layout height after closing.
